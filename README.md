## Slide 1 – Introduction to CCSDS Packet Protocols

### Key concepts
- **CCSDS:** Organization that develops space communication standards.
- **SPP:** Packages and identifies application data into Space Packets.
- **EPP:** Encapsulates higher-layer protocol data units (PDUs).
- **Green Book:** Explains concepts and architecture.
- **Blue Book:** Defines normative protocol requirements.

### Protocol flow

```text
Application Layer
       |
       v
    SPP / EPP
       |
       v
  Data Link Layer
  (TM / TC / AOS)
       |
       v
  Physical Layer
 (RF / Optical)
       |
       v
   Communication
```

### Key takeaway
SPP and EPP standardize how application data is packaged before it is transferred through space communication links.

## Slide 2 – Space Packet Protocol Fundamentals

### Key concepts
- **Space Packet:** Contains a 6-byte primary header and a packet data field.
- **APID:** Application Process Identifier; identifies a packet stream within a mission's naming domain.
- **Packet Data Field:** Contains application data and may include a secondary header.
- **Self-delimited:** Packet length is determined using the primary header's Packet Data Length field.
- **SPP responsibility:** Identifies and encapsulates application data; does not provide network routing.
- **Mission-specific:** APID assignments and packet data formats are defined by the mission.

### Packet structure

```text
       Space Packet
            |
     +------+------+
     |             |
Primary Header   Packet Data Field
   (6 bytes)      (variable length)
     |             |
    APID        Application Data
                + Optional
                Secondary Header
```

### SPP data flow

```text
Source Application
        |
        v
   SPP Entity
(Create / Validate)
        |
        v
   APID-based
   Identification
        |
        v
Underlying Communication
      Services
        |
        v
 Destination SPP
        |
        v
Destination Application
```

### Important formula

`Total Packet Length = 6 + Packet Data Length + 1`

Example: Packet Data Length = 99

Total = 6 + 99 + 1 = **106 bytes**

### Key takeaway
SPP packages and identifies application data. APID identifies packet streams, while the actual communication path is handled by underlying services and mission configuration.

## Slide 3 – SPP Architecture

### Key concepts
- **Application Layer:** SPP directly packages application data into Space Packets.
- **Shim protocol:** SPP carries PDUs generated by upper-layer protocols.
- **PDU:** Protocol Data Unit; data unit belonging to a protocol.
- **SDU:** Service Data Unit; data passed from a service user to a protocol.
- **Encapsulation:** Carrying one protocol's data unit inside another protocol's data unit.
- SPP can occupy either of two architectural positions; both are not mandatory in one path.
- EPP can also operate as a shim protocol.

### Architecture

**Option A – SPP as Application Layer**

```text
Application
     |
     v
    SPP
     |
     v
  Data Link
     |
     v
 Physical
```

**Option B – SPP as Shim**

```text
Upper-layer protocols
  (TCP / UDP / IP / BP)
          |
          v
       SPP Shim
          |
          v
      Data Link
          |
          v
       Physical
```

### Key takeaway
SPP can directly carry application data or act as a shim to carry upper-layer PDUs over CCSDS Space Data Link protocols. It does not replace those upper-layer protocols or provide network routing.

## Slide 4 – APID and Addressing

### Key concepts
- **APID:** 11-bit Application Process Identifier in the Space Packet primary header.
- **APID range:** `0–2047` (2¹¹ possible values).
- **Idle Packet:** APID `2047` (`0x7FF`) is reserved for Idle Packets.
- **Naming domain:** The scope within which APIDs must be unique, such as a spacecraft or constellation element.
- **Mission allocation:** The project defines APID assignments and their meanings.
- **Important:** APID identifies a managed packet stream; it is not a globally unique address or a network-routing mechanism.

### Packet Identification Field

```text
       13-bit Packet Identification Field
  +-------------+----------------+-------------+
  | Packet Type | Secondary      |    APID     |
  |   1 bit     | Header Flag     |   11 bits   |
  |             |   1 bit         |             |
  +-------------+----------------+-------------+
```

### APID-based processing

```text
        Received Space Packet
                 |
                 v
          Read APID field
                 |
                 v
       Mission APID allocation
               table
                 |
        +--------+--------+
        |        |        |
        v        v        v
      APID 100 APID 101 APID 102
        |        |        |
        v        v        v
     Thermal  Battery  Camera
    Processor Processor Processor
```

### Example mission allocation

| APID | Example stream |
|---:|---|
| 100 | Temperature telemetry |
| 101 | Battery telemetry |
| 102 | Camera data |

These are illustrative mission assignments, not predefined CCSDS values.

**Key takeaway:** APID identifies a packet stream within a mission-defined naming domain. The mission controls its allocation and determines how received packets are processed.

## Slide 5 – SPP Services

### 1. Service Access Point (SAP)
- **SAP:** Logical interface between the service user (application) and SPP entity.
- Applications submit SDUs associated with an APID.
- Same SAP: SDUs are processed in submission order.
- Different SAPs: no shared processing-order guarantee.

### 2. Two SPP services

| Service | Input (SDU) | Responsibility |
|---|---|---|
| Packet Service | Preformatted Space Packet | Transfers the packet intact |
| Octet String Service | Sequence of octets | SPP formats the data into a Space Packet |

### 3. Common service characteristics

- **Preconfigured:** Managed data path established by management.
- **Unidirectional:** One direction per managed path.
- **Asynchronous:** No predefined application submission timing.
- **Unconfirmed:** No end-to-end receiver confirmation.
- **Incomplete:** No guarantee that all SDUs arrive; no retransmission mechanism.
- **Non-sequence-preserving:** End-to-end order is not guaranteed.
- **Flow control:** CCSDS does not define flow control between the SPP user and provider.

### 4. Service architecture

```text
       Sending Application
                |
                v
          SPP Service
          (SAP / APID)
                |
                v
         Space Packet
                |
                v
       Underlying Subnetwork
                |
                v
        Destination SPP
                |
                v
      Receiving Application
```

### 5. Bidirectional communication

```text
Spacecraft                    Ground
    |                           |
    |---- Telemetry Path ------>|
    |                           |
    |<--- Telecommand Path -----|
    |                           |

Two separate managed paths,
one for each direction.
```

**Key takeaway:** SPP provides asynchronous, unconfirmed packet transfer. It does not guarantee end-to-end delivery, retransmission, flow control, or sequence preservation. Applications requiring reliability must implement or use additional mechanisms.


## Slide 6 – SPP Reliability and Limitations

### Key Concepts
- **Packet Sequence Count:** 14-bit counter used to number Space Packets within an APID stream.
- **Range:** `0–16383` (2¹⁴ values).
- **Rollover:** After `16383`, the counter returns to `0`.
- **Sequence gap:** May indicate missing packets or another stream discontinuity.
- **SPP limitation:** No guaranteed delivery, automatic retransmission or end-to-end ordering.
- **Reliability:** Additional protocols or mission-specific mechanisms are required.

### Packet Loss Detection

```text
Satellite                 Ground
   |                         |
   |---- Seq 100 ----------->| ✓
   |---- Seq 101 ----------->| ✓
   |---- Seq 102 -----X      | Lost
   |---- Seq 103 ----------->| ✓
   |                         |
   |                   Detect gap
   |                   (101 → 103)
   |                         |
   |                   No automatic
   |                   retransmission
```

### Reliability Mechanisms

| Mechanism | Purpose |
|---|---|
| Sequence Count | Detect possible packet gaps |
| COP-1 | Reliable TC transfer-frame delivery |
| CFDP | File delivery with optional reliability |
| Command ACK | Confirm command status at the defined level |

### Important Distinction

```text
Sequence Count
      |
      v
Detect Possible Loss
      |
      v
Additional Mechanism
      |
      v
Recover Data (if supported)
```

**Key takeaway:** SPP helps identify missing packets but does not recover them. Reliability must be provided by other mechanisms.


## Slide 7 – Satellite Communication Example

### Key Concepts
- **Uplink:** Ground → Satellite (commands).
- **Downlink:** Satellite → Ground (telemetry/images).
- **TC:** Telecommand data-link protocol.
- **TM:** Telemetry data-link protocol.
- **Command ACK:** Mission-defined confirmation of command status.
- **Image transfer:** Large images require segmentation or an appropriate file-transfer mechanism.

```text
          +-------+-------+
                  |

              TM Downlink
                  |
                  v
             GROUND SYSTEM
                  |
          +-------+-------+
          |               |

     Verify Status    Reconstruct

```

### Example APID Allocation

| APID | Purpose |
|---|---|
| 200 | Camera commands |
| 201 | Command status |
| 300 | Camera image data |

*These APIDs are illustrative mission assignments.*

### Important Distinctions
- SPP carries commands but does not execute them.
- TC/TM data-link protocols transport packets over space links.
- Link-layer delivery confirmation ≠ command execution confirmation.
- SPP does not automatically reconstruct images or recover missing data.

**Key takeaway:** SPP identifies and packages application data, TC/TM transfer it over the space link, and mission software interprets commands and telemetry.

## Slide 8 – Encapsulation Packet Protocol (EPP)

### Key Concepts

- **EPP:** Encapsulation Packet Protocol; carries higher-layer PDUs over CCSDS space data links.
- **Purpose:** Allows PDUs without an authorized CCSDS Packet Version Number to use CCSDS packet services.
- **Shim protocol:** EPP operates between upper-layer protocols and the Space Data Link Layer.
- **PVN:** 3-bit Packet Version Number identifying the outer packet format.
  - SPP: `000`
  - EPP: `111`
- **Encapsulation:** Adds an EPP header without modifying the original PDU.
- **One-to-one mapping:** One upper-layer PDU per Encapsulation Packet.

### EPP Architecture

```text
      Upper-Layer Protocol
          (e.g., CFDP)
               |
               v
            CFDP PDU
               |
               v
              EPP
               |
               v
    +---------------------+
    | EPP Header          |
    +---------------------+
    | CFDP PDU            |
    +---------------------+
               |
               v
       Space Data Link
       (TM / TC / AOS)
               |
               v
         RF / Optical
               |
               v
          Destination
```

### SPP vs EPP

| SPP | EPP |
|---|---|
| Can directly carry application data | Encapsulates upper-layer PDUs |
| Can also operate as a shim | Operates as a shim |
| PVN = `000` | PVN = `111` |
| Max packet = 65,536 bytes | Max packet = 4,294,967,287 bytes |

### Important Rules

- EPP preserves the encapsulated PDU unchanged.
- One EPP packet contains exactly one PDU.
- EPP does not provide automatic retransmission.
- Actual packet sizes depend on mission and data-link constraints.

**Key takeaway:** EPP acts as a standardized wrapper that allows protocols such as CFDP to transfer their PDUs through CCSDS Space Data Link protocols.

## Slide 9 – EPP Header and Addressing

### Key Concepts

- **EPP header:** Variable length: 1, 2, 4, or 8 bytes.
- **PVN:** Identifies the packet format (`111` for EPP).
- **Protocol ID:** Identifies the encapsulated protocol.
- **EPI:** Encapsulated Protocol Identifier; identifies the EPP service user.
- **LID:** 2-bit field specifying primary-header length.
- **Protocol ID Extension:** Supports extended protocol identification.
- **Addressing:** EPP does not use APIDs or provide network routing.
- **SAP identification:** Combination of PVN, EPI, and SDLP channel.

### EPP First Byte

```text
             8 bits
+---------+-----------+--------+
|   PVN   | Protocol  |  LID   |
| 3 bits  | ID        | 2 bits |
|         | 3 bits    |        |
+---------+-----------+--------+
```

### Header Length

| LID | Header size |
|---|---|
| 00 | 1 byte |
| 01 | 2 bytes |
| 10 | 4 bytes |
| 11 | 8 bytes |

### EPP Decoding Flow

```text
     Received Packet
            |
            v
       Check PVN
            |
            v
       Decode LID
            |
            v
    Read Header Length
            |
            v
    Read Packet Length
       (if present)
            |
            v
    Identify Protocol
       Using EPI
            |
            v
    Extract Original PDU
            |
            v
    Upper-Layer Handler
       (e.g., CFDP)
```

### Key Takeaway

EPP uses PVN, protocol-identification fields, and LID to identify and extract encapsulated PDUs. The combination of PVN, EPI, and SDLP channel identifies the service access point.



## Slide 10 – Choosing Between SPP and EPP

### Protocol Selection

| Requirement | Suitable choice |
|---|---|
| Housekeeping telemetry | SPP |
| Direct application data transfer | SPP |
| CFDP PDU encapsulation | EPP |
| IP packet encapsulation | EPP |
| APID-based stream identification | SPP |
| Carrying existing protocol PDUs | EPP or SPP shim |

### Decision Flow

```text
        Data to Transfer
               |
               v
      What does the mission
             need?
               |
       +-------+-------+
       |               |
       v               v
  Application      Existing PDU
     Data          (CFDP / IP)
       |               |
       v               v
      SPP         Consider EPP
       |               |
       +-------+-------+
               |
               v
       CCSDS Data Link
               |
               v
        RF / Optical
```

### Engineering Rules

- SPP is useful for application data and APID-based identification.
- EPP is useful for encapsulating existing protocol PDUs.
- SPP can also operate as a shim.
- Both protocols can coexist in one mission.
- Neither provides network routing or automatic retransmission.
- Select the protocol based on mission requirements and supported data-link services.

**Key takeaway:** SPP and EPP solve related but different packaging problems. Choose the protocol that best matches the data format and mission architecture.


## Slide 11 – Reliability, Real-Time and Large Data Transfers

### Key Concepts

- **CFDP:** File transfer protocol; acknowledged mode supports recovery of missing file data.
- **LTP:** Supports communication over long-delay links, with reliability for selected data.
- **Virtual Channel (VC):** Logical data-link channel used to separate traffic streams.
- **DTN:** Networking approach for intermittent or disrupted connectivity.
- **Bundle Protocol:** Supports store-and-forward communication.
- **Real-time:** SPP/EPP do not guarantee maximum delivery delay.

### Communication Architecture

```text
        Spacecraft Applications
                  |
        +---------+---------+
        |                   |
        v                   v
     Telemetry          Image File
        |                   |
        v                   v
       SPP                 CFDP
        |                   |
        |                   v
        |                  EPP
        |                   |
        +---------+---------+
                  |
                  v
        CCSDS Data Link
         (Virtual Channels)
                  |
                  v
           Physical Link
                  |
                  v
            Ground System
```

### Choosing the Right Mechanism

| Requirement | Mechanism |
|---|---|
| Regular telemetry | SPP |
| Reliable file transfer | CFDP acknowledged mode |
| Long-delay communication | LTP |
| Traffic separation | Virtual Channels |
| Intermittent connectivity | DTN / Bundle Protocol |
| Prioritized telemetry | High-priority Virtual Channel |

### Large Data Segmentation

```text
         Large Image
              |
              v
       Split into Segments
              |
      +-------+-------+
      |       |       |
      v       v       v
    Seg 1   Seg 2   Seg 3
      |       |       |
      v       v       v
   Packet  Packet  Packet
      |       |       |
      +-------+-------+
              |
              v
         Ground System
              |
              v
       Reconstruct Image
```

- SPP Sequence Flags can identify the first and last segments.
- A secondary header can carry mission-defined segment information.
- Reconstruction requires suitable application logic.
- Packet size must respect the implementation's supported limits.

### Important Distinctions

- **SPP/EPP:** Packet transfer and encapsulation.
- **CFDP:** File delivery.
- **LTP:** Reliable transfer across suitable long-delay links.
- **Virtual Channels:** Data-link traffic organization.
- **DTN:** Communication across disrupted networks.

**Key takeaway:** SPP and EPP provide packet transfer, while additional protocols and data-link mechanisms address reliability, file delivery, prioritization, and intermittent connectivity.

### Important Engineering Rules

- **Space Packet ≠ Transfer Frame.**
- APID identifies packet streams; VCID identifies data-link channels.
- SPP/EPP do not provide network routing.
- Packet delivery does not guarantee command execution.
- SPP/EPP do not guarantee delivery or automatic retransmission.
- Mission software defines command and telemetry formats.
- Use the relevant CCSDS Blue Books for implementation requirements.

### Final Takeaway

**Application → Packet Protocol → Data Link → Physical Link → Ground Processing**

Each layer has a specific responsibility. Understanding these boundaries is essential when designing or debugging satellite communication software.
